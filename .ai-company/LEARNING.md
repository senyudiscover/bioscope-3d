## L-001 · 为什么要把项目状态写进文件，而不是留在聊天里（2025-09）

### 这次发生了什么

之前项目状态只存在于一段段聊天记录里。换一个 AI 会话、换一个 Agent（Codex / GLM），
它们读不到之前的聊天，只能靠猜测或重新读代码。上一轮就因此出现了
"半迁移状态"——类型定义改好了、数据没改，导致编译失败。

所以现在建立了 `.ai-company/` 目录，把"项目是什么、做到哪了、下一步做什么、
做过哪些决定、谁负责什么"写进文件。以后任何 Agent 接手，先读这些文件就能恢复上下文。

### 你应该理解的 1–3 个概念

1. **Source of truth（事实来源）**：一个团队里"到底听谁的"必须唯一。
   这里定为：**代码 + 项目文件是事实来源，聊天记录不是**。
2. **上下文恢复（context recovery）**：AI Agent 每次都是"失忆"的，
   它恢复记忆的方式就是读文件。所以关键状态必须落盘。
3. **单一职责的文件**：PROJECT 讲"是什么"，BOARD 讲"做什么"，DECISIONS 讲"为什么"。
   分开写，比塞进一个大文件更容易维护和查找。

### 为什么代码这样设计

不是代码设计，是**工作方式**设计：把"容易被聊天遗忘的信息"变成"持久化文件"，
让跨 Agent、跨平台协作成为可能。

### 如果我以后自己修改，应该从哪里看

先看 `.ai-company/PROJECT.md`（快速了解），再看 `BOARD.md`（当前任务），
最后看 `AGENTS.md`（各自职责）。

### 推荐我掌握到什么深度

理解"为什么要有 source of truth"就够了，不需要会写这些文件的模板。

## L-002 · 两条构建路径的区别（2025-09）

### 这次发生了什么

发现项目有两条"打包成可运行网站"的命令：`npm run build`（生产）和
`npm run local-build`（本地预览）。它们是两套不同的东西。

### 你应该理解的 1–3 个概念

1. **Build（构建）**：把开发者写的 TypeScript/JSX 源码，编译成浏览器能直接跑的
   静态文件（HTML/CSS/JS）的过程。
2. **SPA vs RSC**：
   - SPA（单页应用）：整个应用打包成一个 JS，浏览器下载后自己渲染。
     `local-build` 走这条，简单、适合本地快速预览。
   - RSC（React Server Components）：部分组件在服务器上渲染。
     `vinext build` 走这条，配合 Cloudflare 部署，适合正式上线。
3. **publicDir（静态资源目录）**：构建时"原样拷贝"到产物的文件目录。
   本地预览的 3D 模型文件（`local-public/models/*.glb`）就是这样被带进去的。

### 为什么代码这样设计

本地要快、要简单，所以用纯 SPA；生产要考虑部署到 Cloudflare、要做服务端渲染，
所以用 vinext + RSC。两条路径解耦，互不干扰。

### 如果我以后自己修改，应该从哪里看

`vite-spa.config.ts`（本地 SPA）、`vite.config.ts`（生产 vinext）、
`package.json` 的 scripts 字段。

### 推荐我掌握到什么深度

能说清"本地预览用 local-build，上线用 build"即可，RSC 的内部原理暂时不用深入。

## L-003 · 为什么 AI 会"改坏"一个原本能跑的项目（2025-09）

### 这次发生了什么

上一轮 AI 会话因为输出 token 上限中断，留下"类型定义已改、数据没改"的半完成状态，
导致 `tsc` 报一堆错。这次接手后第一件事就是**先跑 `npx tsc --noEmit` 看真实状态**，
而不是相信"上一轮应该改完了"。

### 你应该理解的 1–3 个概念

1. **Type checking（类型检查）**：`tsc --noEmit` 只检查类型对不对，不产出文件。
   它是判断"代码能不能编译"最直接的手段。
2. **半完成状态（partial migration）**：一次改动涉及多个文件时，AI 可能只改了一半就断了。
   这时项目既不是旧版也不是新版，而是"坏的中间态"。
3. **以磁盘为准**：永远以当前文件实际内容为准，不假设"上次成功/失败了"。

### 为什么代码这样设计

（本条不是设计，是协作教训。）经验：**任何大改动前先跑一遍 tsc 建基线**，
改完再跑一遍，能立刻暴露半完成状态。

### 如果我以后自己修改，应该从哪里看

在项目根目录跑 `npx tsc --noEmit`；报错会精确到文件:行号。

### 推荐我掌握到什么深度

会跑 `npx tsc --noEmit` 并能看懂"报错在哪个文件哪一行"即可。
